001 — Авторизация с некорректным номером телефона
Цель: проверить валидацию номера телефона при входе.

Предусловия:
* приложение установлено
* пользователь не авторизован

Шаги:
1. Запустить приложение
2. Перейти в экран входа
3. Ввести некорректный номер телефона, например:
   * меньше нужного количества цифр
   * буквы вместо цифр
   * спецсимволы
4. Нажать кнопку продолжения / получения кода

Ожидаемый результат:
* приложение не отправляет запрос на авторизацию
* отображается сообщение о некорректном формате номера
* кнопка продолжения неактивна или появляется ошибка валидации

# Негативные тест-кейсы с использованием Proxyman

001 — Обработка серверной ошибки 500 при открытии карточки товара

Цель: проверить реакцию приложения на внутреннюю ошибку сервера при загрузке товара.

Предусловия:
* Proxyman настроен
* сертификат установлен
* найден запрос карточки товара

Шаги:
1. В Proxyman найти запрос, который открывает карточку товара
2. Включить **Breakpoint → Response**
3. Открыть карточку товара в приложении
4. В Breakpoint Editor изменить статус ответа с `200` на `500`
5. Выполнить запрос

Ожидаемый результат:
* карточка товара не загружается
* отображается корректное сообщение об ошибке или экран ошибки
* приложение не падает
* не отображаются битые или частично сломанные данные

---

002 — Пустой список товаров через Map Local

Цель: проверить отображение пустого состояния каталога.

Предусловия:
* Proxyman настроен
* найден запрос списка товаров

Шаги:
1. Сохранить response каталога через **Save Response**
2. Открыть JSON-файл
3. Очистить массив товаров
4. Подключить измененный файл через **Map Local**
5. Открыть каталог в приложении

Ожидаемый результат:
* приложение корректно обрабатывает пустой список
* отображается состояние “товары не найдены” / “нет данных”
* интерфейс не ломается
* не возникает бесконечная загрузка

---

003 — Подмена ответа поиска на некорректный JSON

Цель: проверить устойчивость приложения к невалидному ответу сервера.

Предусловия:
* Proxyman настроен
* найден запрос поиска

Шаги:
1. Включить **Breakpoint → Response** на запросе поиска
2. В приложении выполнить поиск товара
3. В ответе заменить корректный JSON на некорректный, например:
```json
{ "products": [ }
```
4. Выполнить запрос

Ожидаемый результат:
* приложение не падает
* отображается ошибка загрузки или пустое состояние
* пользователь не видит сломанный интерфейс
* приложение продолжает работать после ошибки

005 — Длинное или некорректное значение параметра поиска через Breakpoint Request

Цель: проверить устойчивость поиска к пограничным входным данным.

Предусловия:
* Proxyman настроен
* найден запрос поиска

Шаги:
1. Включить Breakpoint → Request на запросе поиска
2. В приложении выполнить обычный поиск
3. В Breakpoint Editor заменить параметр поиска на:
   * очень длинную строку из 200–500 символов
   * спецсимволы
   * HTML/SQL-подобную строку
4. Выполнить запрос

Примеры:

```text
@@@@@@@@@@@@@@@@@@@@@@@@@@@@
```

```text
' OR 1=1 --
```

```text
<script>alert(1)</script>
```

Ожидаемый результат:
* приложение не падает
* серверный ответ обрабатывается корректно
* не появляется сломанная верстка
* если результатов нет, показывается корректное пустое состояние или сообщение об ошибке
 Высокий
